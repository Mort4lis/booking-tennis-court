# booking-tennis-court

Production-ready template for a Telegram bot that books a tennis court. It is a scaffold: layers, wiring, config,
observability, migrations and tooling are in place, but there is **no business logic** — handler/service/repository
bodies are stubs marked as extension points.

## Go development

Before any Go coding, review, debugging, troubleshooting, or setup task, load the
`samber/cc-skills-golang@golang-how-to` skill first — it routes to whichever other Go skills the task needs.

## Architecture

Clean Architecture, dependencies point inward (`transport → service → repository`, all sharing `dto`/`entity`). Ports
are declared by the consumer: `service/booking`
defines its `Repository` interface, `transport/telegram` defines `BookingService`. Dependency injection via
`samber/do/v2`: the whole graph is registered **in one place** (`internal/app/deps`) — no per-layer `do.Package`.
Providers are lazy, but
`deps.New` eagerly instantiates every long-lived service so wiring/connection errors surface at startup; samber/do then
drives shutdown in reverse invocation order via each service's `Shutdown` hook (no hand-rolled shutdown registry).

| Path                              | Responsibility                                                |
|-----------------------------------|---------------------------------------------------------------|
| `cmd/bot`                         | entrypoint; builds the cobra root command only                |
| `internal/cli`                    | commands: `serve`, `migrate up`/`down`, `version`             |
| `internal/config`                 | env config, prefix `BTC_`, `kelseyhightower/envconfig`        |
| `internal/app`                    | runtime lifecycle / graceful shutdown (`Run`)                 |
| `internal/app/deps`               | DI composition root: provider registration + `Container`      |
| `internal/transport/telegram`     | `go-telegram/bot` long-polling transport (thin handlers)      |
| `internal/service/booking`        | application use-cases                                         |
| `internal/repository/booking`     | `pgx` persistence                                             |
| `internal/dto`, `internal/entity` | transport contracts and domain types                          |
| `internal/observability`          | slog logger, OTel metrics (Prometheus endpoint), OTLP tracing |
| `pkg/postgres`                    | reusable pgx pool constructor (no `internal/` imports)        |
| `migrations`                      | embedded SQL migrations, timestamped filenames                |

## Conventions

- Environment variables are prefixed `BTC_` and grouped by sub-struct (`BTC_TELEGRAM_TOKEN`, `BTC_POSTGRES_DSN`,
  `BTC_POSTGRES_MAX_CONN_LIFETIME`).
- Migration files: `<YYYYMMDDHHMMSS>_<name>.{up,down}.sql`
  (`migrate create -ext sql -dir migrations -format 20060102150405 <name>`).
- Every exported symbol has a doc comment; errors are wrapped with `%w` and either returned or logged, never both.
- Stubbed methods (`repository.Create`, `service.CreateBooking`) return the package-local `errNotImplemented` — that is
  the extension point.
- Mocks are generated by mockery v3 (`.mockery.yml`, pinned as a `go tool`). Each mock lands in the package that
  declares the interface, in a
  `mocks_test.go` file (`MockRepository`, `MockBookingService`). Regenerate with `make generate`; add new ports to the
  `packages` list in `.mockery.yml`.
